# Atlas interview demonstration runbook

Run all commands from the root of `ManoochTayebi/Multi_agent_client`. All customers, catalog records, policies, carriers and payments are fictional. No public hosting is required by the Saegus brief. The business clock must remain **2026-10-26** for the included return scenarios.

## 1. Install and choose the execution mode

Python 3.12+:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.lock
pip install '.[dev,browser]'
python -m playwright install chromium
```

For a **new checkout**, copy one example to `.env` (do not overwrite an existing configured `.env`):

```bash
cp .env.example .env                 # deterministic software demonstration
# OR cp .env.local.example .env      # actual Ollama inference and semantic embeddings
```

Replace `ADMIN_API_KEY` in `.env` with a random value, for example one generated by `python -c "import secrets; print(secrets.token_urlsafe(32))"`. Keep it private; it is entered in Operations. Never commit `.env` or paste provider keys into prompts.

| Variable | Deterministic mode | Real local AI mode |
|---|---|---|
| `ATLAS_MODE` | `demo` | `llm` |
| `OPENAI_BASE_URL` | unused | `http://localhost:11434/v1` |
| `OPENAI_API_KEY` | unused | `ollama` (local compatibility placeholder) |
| `OPENAI_MODEL` | unused | `atlas-local` |
| `EMBEDDING_MODEL` | blank: explicitly lexical vectors | `all-minilm`: actual semantic embeddings |
| `LLM_TOKEN_PARAMETER` | unused | `max_tokens` |
| `LLM_REASONING_EFFORT` | unused | `none` for the supplied Qwen3 model |
| `LLM_JSON_SCHEMA` | unused | `true` |
| `LLM_TIMEOUT_SECONDS` / `LLM_MAX_TOKENS` | unused | `180` / `800` |
| `LLM_MAX_RETRIES` | unused | `0`; specialist repair remains bounded separately |
| `DEMO_ACCESS` | `true` for synthetic customer selection | `true` for synthetic customer selection |
| `AS_OF_DATE` | `2026-10-26` | `2026-10-26` |
| `ADMIN_API_KEY` | your generated operator key | your generated operator key |
| `CARRIER_BASE_URL` | `http://127.0.0.1:8001` for the mock API | same |

A compatible remote provider can replace the local URL/model/key. Use the token parameter and schema/reasoning settings supported by that provider. Set cost rates only when known; unknown estimates remain null. Ollama can use zero provider inference charges, but hardware/electricity costs are not measured.

## 2. Start real models (LLM mode only)

Install Ollama using its official installer. Terminal 1:

```bash
ollama serve
```

Skip `serve` if the desktop application already serves port 11434. Terminal 2:

```bash
ollama pull qwen3:1.7b
ollama pull all-minilm
ollama create atlas-local -f models/Modelfile
ollama list
curl --fail http://localhost:11434/api/tags
```

The first startup can download roughly 1.5 GB of model data. No model weights are stored in Git. A model being installed is not evidence that a journey passed: run the actual LLM evaluation below.

## 3. Start the mock carrier and initialize fresh demo state

Terminal 2, after downloads complete:

```bash
source .venv/bin/activate
python -m uvicorn atlas.mock_carrier:app --host 127.0.0.1 --port 8001
```

Terminal 3:

```bash
source .venv/bin/activate
export AS_OF_DATE=2026-10-26
export CARRIER_BASE_URL=http://127.0.0.1:8001
export NO_PROXY=localhost,127.0.0.1
export ATLAS_REHEARSAL=$(date +%Y%m%d_%H%M%S)
export DATABASE_URL="sqlite:///runtime/rehearsal_${ATLAS_REHEARSAL}.db"
export CHROMA_PATH="runtime/rehearsal_${ATLAS_REHEARSAL}_chroma"
python -m uvicorn atlas.api:app --host 127.0.0.1 --port 8000
```

A new SQL filename and Chroma directory give a clean rehearsal without deleting prior evidence. Startup verifies data checksums, seeds the empty database, indexes policies and products, and loads the configured embedding model. In semantic mode, indexing must succeed; there is no silent lexical substitute.

Open **http://localhost:8000**. Check **http://localhost:8000/health**: `status=ok`, the intended `mode`, `payments=simulation`, and the fixed synthetic clock. The header and each response label the execution mode. Swagger: **http://localhost:8000/docs**.

## 4. Demo A — €249 refund with human approval

Select **C0001**. Click “Demo A” or enter:

> I would like a refund for order O1002.

Expected business evidence and behavior:

1. Orchestrator selects Returns Investigation; Resolution follows its verified evidence.
2. Investigation returns the owned SQL order, `total_cents=24900`, verified condition/delivery and cited `returns.md` policy. The EUR 150 threshold requires review.
3. Guardrails pass. In LLM mode a separate Judge call checks the draft reply; inspect `judge` and model events for `JudgeVerdict`. Demo mode explicitly reports that no LLM Judge ran.
4. The customer sees a **proposal**, EUR 249, required human review, and “Confirm refund proposal.” No payment has occurred.
5. Click confirmation. Status becomes **Confirmed · awaiting human review**.
6. Open **Operations**, enter the operator key and load the queue. Enter a reason such as “Verified synthetic receipt and warehouse inspection,” then approve or reject.
7. After approval, click **Process simulated payments**. One simulated transaction completes; repeat processing must report zero.
8. Inspect “Audit events — last selected request.” It shows proposal, customer confirmation, reasoned operator decision and simulated completion. “View audit trail” is also available on pending requests.

Rejection must produce no transaction. Approval before customer confirmation, unauthorized admin calls and duplicate confirmations are checked automatically by the API integration suite. A rejected action remains rejected. A repeat request reuses the existing action and reports its pending/rejected/queued/completed simulation status; reset state to rehearse a fresh lifecycle.

**Failure conditions:** no owned order; wrong amount; missing policy evidence; Judge unavailable/rejecting; action published despite failed guardrails; approval before customer confirmation; processing before approval; duplicate transaction; a statement that real money moved. A blocked Judge result must show human support and no new proposal, not a claimed success.

## 5. Demo B — measured parallel tracking and styling

Customer **C0001**, exact prompt (also the Demo B button):

> Track my order O1001 and build a smart casual outfit under €150, size M.

Expected:

- Orchestrator activates **Order Tracking** and **Product Discovery** as independent workers, then **Personal Stylist**. No returns/resolution activation is needed.
- Tracking verifies owned O1001 and reports delivered status, labeled `live mock carrier API` when the mock service is running. A cached fallback must be labeled.
- Discovery shows SQL variants and Chroma retrieval distances; `retrieval_mode=semantic` only when the semantic encoder is configured. Demo mode is explicitly lexical.
- Stylist chooses exact variants from Discovery after Discovery finishes. SQL/Python checks validate current IDs, size M, positive stock, composition and total price **≤ EUR 150**.
- The reply contains **both** shipment status and the outfit result. The multi-intent LLM flow invokes the Judge.

Inspect “Inspect orchestration & evidence”: `trace` contains monotonic `started_ms`, `ended_ms`, execution mode, selected tool calls and sources. `execution_summary.parallel_pairs` records measured overlap. Verify:

```text
max(tracking.start, discovery.start) < min(tracking.end, discovery.end)
stylist.start >= discovery.end
```

These are measurements, not added sleeps in the real demo. The concurrency unit test uses a barrier to prove workers truly execute concurrently. The graph currently joins all independent evidence before downstream resolution/styling; it does not promise the stylist starts immediately when discovery finishes. Parallel graph execution also does not guarantee that a local model server runs inference requests simultaneously.

**Failure conditions:** wrong/extra routing; absent tracking or outfit answer; missing dependencies; no overlapping workers; invented/stale variants; wrong size; zero stock; budget exceeded; unlabeled fallback. A recovered answer may still be usable, but a fallback fails **strict real-LLM acceptance**.

## 6. Direct human assistance

Use an authenticated customer such as **C0001**. Select **Talk to a person** or enter:

> I want to speak to a real agent.

The explicit request works in demo and LLM modes without requiring model inference. It is intentional control routing, not a deterministic recovery after a failed model call. French example: “Je veux parler à un conseiller humain.”

1. Verify **Waiting for a human operator**. The trace shows the Orchestrator and its `human_handoff` control step, with a persisted support-thread ID, no specialist findings, no new financial action and zero model calls for the explicit request.
2. Open **Operations**, enter `ADMIN_API_KEY`, then select **Load support queue** → **Open conversation**. Inspect **Conversation context, evidence & support audit** for prior customer/assistant messages, run reports, SQL/RAG evidence and requested events.
3. Verify **Send human reply** is disabled while waiting. Choose **Take over conversation**. The state becomes `active` and records a `claimed` event.
4. Type a real operator response in **Reply to customer**, then select **Send human reply**. Return to Customer workspace; within the three-second polling interval the message appears labeled **Human operator**.
5. Send another customer message in the composer, including an order/refund request if desired. It appears in the human transcript and stays on the human route. It must not activate specialists, create a new proposal or authorize payment.
6. Refresh the browser. The same tab-scoped session and saved human conversation should return. SQL also preserves the conversation across an application restart.
7. Close from Operations with a nonblank **Closing summary**, or select **Return to AI concierge** as the customer. A `closed` event and system summary are recorded. Send “Track O1001”; normal AI routing should resume on this next request.

The queue is separate from **Load review queue** for confirmed financial proposals. A human message saying “approved” cannot replace the confirmation, approval and simulation controls. A Resolution `human_support` decision or failed quality gate opens the same support queue with its recorded escalation reason.

API equivalents are documented in [Architecture §6](ARCHITECTURE.md#6-human-conversation-lifecycle). Direct handoff uses the existing authenticated interface:

```bash
curl --fail http://localhost:8000/api/chat \
  -H "Authorization: Bearer ${ATLAS_SESSION_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"message":"I want to speak to a real agent.","request_human":true}'
curl --fail http://localhost:8000/api/support \
  -H "Authorization: Bearer ${ATLAS_SESSION_TOKEN}"
```

Set `ATLAS_SESSION_TOKEN` privately to the token returned by `/api/sessions`; do not commit it or include it in reports. Operator endpoints require `X-Admin-Key` and cannot be called with the customer bearer alone.

Failure conditions: a queued request claimed as already connected, an operator reply accepted before takeover, another session seeing the transcript, continued specialist execution while waiting/active, a handoff authorizing payment, or lost messages after refresh/restart. No operator notification, external helpdesk or guaranteed response time is implemented. During an in-flight request, another same-session mutation returns 409; wait for it to finish before requesting takeover.

## 7. Inspect and record real interfaces

Customer UI trace JSON includes plan/routing reasons, tool calls, order/product facts, retrieval text/source hashes, separate guardrails and Judge verdict, model/embedding calls and usage, and measured parallel/dependency evidence. Traces describe completed execution; the interface does not stream internal steps live.

For API use, create a session via `POST /api/sessions` with `{"customer_id":"C0001"}`. Send its token as `Authorization: Bearer <session-token>` to `POST /api/chat` with `{"message":"<exact prompt>"}`. The session token is a credential: do not include it in public reports. `GET /api/history` retrieves saved run evidence for that session.

Customer confirmation is `POST /api/actions/<id>/confirm`. Admin endpoints require `X-Admin-Key`: `GET /admin/reviews`, `POST /admin/actions/<id>/decision` with `{"approve":true,"reason":"verified synthetic inspection"}`, `POST /admin/outbox/drain`, and `GET /admin/audit/<id>`. Aggregate monitoring: `GET /metrics` with the same operator header. The automated runner below exercises these endpoints without exposing credentials.

## 8. Automated rehearsals and reports

```bash
ruff check atlas scripts tests
pytest -q
python -m scripts.evaluate --mode demo
python -m scripts.evaluate --mode demo --suite journeys --repeat 3 --output reports/demo-journeys.json
python -m scripts.browser_demo --output reports/browser-demo.json
```

The API runner starts the actual application through its test transport and uses isolated SQL/index stores for each repeat. It does not fake graph nodes. The Chromium runner starts isolated real HTTP API and mock-carrier processes, exercises the refund and parallel-styling journeys plus human takeover/reply/closure and session restoration, verifies audit/idempotency/overlap and records JSON plus desktop/mobile screenshots. It always labels its mode **demo** and stops its subprocesses afterward. Run browser rehearsals from the repo after a **non-editable install** as above; it also verifies installed code works outside the checkout.

For real inference with `.env.local.example` settings configured:

```bash
python -m scripts.evaluate --mode llm --suite journeys --repeat 3 --output reports/llm-journeys.json
```

Strict success requires exact roles, relevant actual model stages/native tool calls, semantic retrieval configured/executed, no deterministic fallback, valid business rules and completed approval/dependency journeys. Reports include source hashes, agent timings, chat/embedding calls/tokens, cost estimates (null when unknown), retrieval relevance probes, extra-agent activations, fallback rate, business/authorization check failures and the actual evidence/audit. API/index startup time is excluded from per-request latency; per-run embedding usage excludes initial indexing.

Read failed checks and warnings, not only aggregate pass rate. These curated scenarios are not an independent benchmark or proof of production safety. Historical reports in `docs/validation/evaluation-llm*.json` describe earlier executions; compare source hashes before attributing them to the current code.

## 9. Reset, troubleshoot and present honestly

- **Every message stays in human support:** close the waiting/active conversation or choose **Return to AI concierge**. This is intentional suspension, not a routing failure.
- **No operator reply arrives:** verify the request appears in **Load support queue**, take it over, send a reply and check the operator key/network. Waiting alone does not mean a person has joined.

- **Reset:** stop the API with Ctrl+C, run section 3 again with a new rehearsal timestamp, restart the API and reconnect C0001. Stop an automated/browser runner before starting another on the same explicit port. Existing rehearsals remain available for inspection.
- **Model unavailable:** check `ollama list`, `/api/tags`, model name and server port. Verify `atlas-local` was created and the embedding model was pulled. Remote providers need their actual credentials. No current endpoint means live validation is unavailable, not passed.
- **Slow inference:** warm the model with a genuine rehearsal before the interview; use the two focused journeys. Keep a saved successful trace as an explicitly recorded backup, separate from the live request. If necessary, demonstrate the complete deterministic workflow and explain the real-model evidence and latency limitations. Never label a recording or fallback as live strict LLM success.
- **Startup/index errors:** inspect the terminal for embedding/model availability, missing `data/`, file checksums and incompatible dependencies. Use the pinned Python dependencies; do not silently disable semantic retrieval to make an LLM report pass.
- **Database locked/wrong scenario:** use one API process and a fresh SQLite path, avoid sharing rehearsal files across parallel processes, and verify fixed `AS_OF_DATE`. PostgreSQL is supported via Compose but is not required for the interview.
- **Session deletion returns 409:** a chat is still active. Wait for it to finish and retry deletion; the server prevents deletion racing with memory writes.
- **401/403:** reconnect an expired customer session, verify the operator key and use the correct header. Protected mode also requires configured `CUSTOMER_TOKENS`; synthetic demo mode intentionally permits account selection.
- **No refund button:** inspect guardrails/Judge and `human_support` recommendations. Do not bypass them. Check whether an existing action was already approved/rejected/completed.
- **Carrier offline:** start terminal 2, check `http://localhost:8001/health`; cached records remain clearly labeled.
- **Browser missing:** run `python -m playwright install chromium`; on Linux use `python -m playwright install --with-deps chromium` if system libraries are missing.
- **CI import error:** install the repository non-editably (`pip install '.[dev,browser]'`) and verify `from scripts.evaluate import overlap` outside the checkout. Do not add `sys.path` hacks or remove the overlap test.
- **Docker:** `docker build -t atlas:demo .`, then `docker run --rm -p 127.0.0.1:8000:8000 --env-file .env atlas:demo`. Use a demo `.env` for no external credentials; containers need a reachable host URL for Ollama rather than container localhost. Compose already supports a configured `OPENAI_BASE_URL`. Check `docker inspect` health status. No local Docker executable means use the verified CI container job and state that limitation.
